Eviplex Field-Level Encryption

Google Cloud stores and runs Eviplex conversations. This design keeps Google from being able to read them, so storing them there is not a disclosure under § 203 StGB, even without a Google confidentiality agreement. Patient fields are encrypted in the backend before they reach any Google storage, with keys that live outside Google.

Based on fomf-code/meviq main @ c91464e · drafted 2 Nov 2026 · not yet reviewed by legal

At restApp-level field encryptionPer-conversation key, AES-256-GCM, applied in the repositories before every write.
In useConfidential GKE NodesThe CPU encrypts node memory, so plaintext and unwrapped keys never sit in memory Google can read.
In transitL4 passthroughThe load balancer forwards TLS untouched. TLS ends inside the pod, not at Google's front end.

Target architecture

Plaintext exists in two places only: CPU-encrypted pod memory, and the prompt sent to OpenAI under the signed § 203 agreement. Everything Google stores is ciphertext.

One chat turn

The key service is called only when the conversation's key isn't already cached. Decryption and encryption happen in pod memory.

Key hierarchy

Two levels. One master key (KEK) outside Google wraps a data key (DEK) per conversation. Deleting a conversation means destroying its key.

What gets encrypted

All of it lives in the chat schema. No SQL query searches message content, and access runs through about six repositories, so one Drizzle column type (encryptedText / encryptedJsonb) covers it.

What Google can still see

Google can see

  • TLS bytes passing through the L4 load balancer
  • Ciphertext in Cloud SQL, Cloud Storage and backups
  • Wrapped DEKs
  • Encrypted node memory
  • Metadata: who wrote when, how many messages, sizes

Google cannot read

  • The KEK, which never leaves the external HSM
  • Unwrapped DEKs, which exist only in CPU-encrypted memory
  • Questions, answers, titles, summaries, patient names

Open points

  • Residual risk
    The GKE control plane is Google-operated.

    Someone with control-plane access could exec into a pod or schedule a debug pod. Mitigate with Access Approval and Access Transparency, or move the crypto layer into Confidential Space.

  • Residual risk
    The KMS credential lives in the pod.

    Bind it to the workload identity, allowlist the cluster's egress IPs at the KMS, and use attestation-bound access where the vendor supports it.

  • Residual risk
    Old backups and copies hold plaintext.

    Cloud SQL backups and point-in-time recovery from before the migration stay readable until retention expires. Preview and PR environments must never get prod copies.

  • Residual risk
    Logs.

    No conversation content may go to stdout, which ends up in Cloud Logging.

  • Trade-off
    L4 passthrough drops Cloud Armor and Google-managed certificates.

    WAF rules and certificate rotation move into the cluster.

  • Decision
    Where the KEK lives.

    An external KMS called directly (recommended) or Cloud EKM. With Cloud EKM, the unwrapped DEK briefly passes through Google's KMS service.

  • Legal
    No case law on confidential computing yet.

    Risch-Kerst should confirm that this design rules out "Offenbaren" before the Plus/Pro tiers rely on it.

  • Scope
    Patient Context (Plus/Pro) is not on main yet.

    It will hold named patient records and documents. Build encryption into it from day one.

Rollout

  1. Set up the external KMS

    Pick the vendor, create the KEK, and connect the cluster over mTLS.

  2. Harden the runtime

    Move the backend node pool to Confidential GKE Nodes. Switch ingress to L4 passthrough with TLS ending in the pod.

  3. Add encrypted columns and dual-write

    Add dek_wrapped and ciphertext columns. Write both old and new columns through the new column type in the repositories.

  4. Backfill

    Re-encrypt existing rows and GCS objects in a background job.

  5. Switch reads and drop plaintext

    Read from the encrypted columns only, then drop the old ones.

  6. Let old backups expire

    Once retention has passed, record the setup for the DPA and the tech fact sheet.
